# Bake-off round 2: Qwen3.8-27B and Qwen3.5-122B-A10B on the same six tasks

*Name: provisional (2026-09-27, UTC). Round 2 of the two-stage bake-off
[2026-09-27-qwen3-coder-bakeoff.md](2026-09-27-qwen3-coder-bakeoff.md) approved that day. Same six
tasks, same isolation and gate-first grading; deviations below.*

## The question, and the answer

Can either of the two smaller shortlisted models (1x-GPU and 128GB-tier candidates) do this tree's
gated mechanical work well enough to justify hardware, where round 1's 480B model could not?
**No, on this evidence, and it is worse than round 1 hoped.** Qwen3.8-27B got 3 of 6 correct;
Qwen3.5-122B-A10B got 2 of 6. Both models independently made the *same* wrong-paragraph mistake on
one task, and the 122B model's citations fix has a real logic bug that a basic test missed. Neither
clears round 1's own three-or-fewer stop line as a pass; both are at or under it.

## What ran

Both routes were live through the cordoba gateway before this round started (verified by calef's
homelab agent against `~/projects/homelab/open-lane-gateway-spec.md`): `open-lane-qwen38`
(`openrouter/qwen/qwen3.8-27b`, pinned `order: [deepinfra]`) and `open-lane-qwen35-122b`
(`openrouter/qwen/qwen3.5-122b-a10b`, pinned `order: [atlas-cloud, novita]`). One correction to the
brief this lane was given: it named Parasail as qwen38's pinned provider; the live gateway config
pins DeepInfra. Functionally it doesn't matter (see caching, below), but the name is wrong somewhere
upstream of this lane.

Harness: `helpers/open-lane.sh` from the gate-locked branch `lane/open-lane-gate-lock` (PR #1429,
still open, not yet merged at run time). It judges a clean copy of the committed HEAD. It refuses a
round that edits gate machinery (`script/`, `helpers/`, …) unless the brief names the file on a
`Gate target:` line. `--effort low`, reasoning left on (both models are thinking models by default
on these routes; no separate toggle was sent). Isolation matches round 1: a bare `git init` +
`git fetch <sha>` clone per task-model pair, no remote, no QEMU, `script/test`/`script/verify`
forbidden in the brief.

Deviation from round 1, one round not four, and a 25-minute wall cap, not 45. Both are time budget
calls, not measurement. This lane had far less wall-clock than round 1's. The harness's own
retry-with-feedback loop only fires after a full round completes, so a single round already shows
whether the model can do the task at all. A tighter cap changes what a timeout costs, not what a
completed answer's correctness means. The two tasks that hit the cap after already committing
correct work, both models' `f801`, were independently re-verified against a clean gate re-run
outside the timed window, below.

Deviation: briefs were reconstructed, not reused verbatim. Round 1's original session transcripts
for these six tasks live in a lane scratch directory that no longer exists. This round's briefs were
rebuilt from the merged pull requests' own bodies, commit messages and diffs (all six are named and
dated in round 1's table), phrased as problem statements rather than solutions. Two (`1214`, `f801`)
needed an explicit `Gate target: script/citations` line, since their whole point is editing gate
machinery the lock would otherwise refuse.

A process note, since it cost real time and about USD 3 of the total below. A forked subagent,
dispatched mid-run for one narrow lookup (the 122B DGX Spark rate, see below), inherited this lane's
full context, including its scratch scripts and clones. Sharing this machine's process table and
filesystem with the fork, it ran its own concurrent `open-lane` attempts against the same paths. That
corrupted one clone and deleted the lane's own scratch directory once. The lane rebuilt in a fresh,
uniquely-named directory and re-ran the affected task cleanly. The wasted spend is included in the
totals below rather than subtracted out.

What each wrong answer did, verified against the clone:

- #1214. Passed every case the brief listed by hand, but the check compares the *set* of cited
  numbers in a file before and after, not per-line occurrences. Adding a duplicate, unglossed
  citation of a milestone number to `notes/citations.md` (a file that already cites that same
  number once, elsewhere, as an example) is silently missed, because the set of cited numbers in
  that file doesn't change. On a fresh file with no prior citations the same edit is caught
  correctly (verified both ways). This is exactly the failure shape this task exists to prevent,
  just for a narrower trigger than round 1's.
- #1201. The identical mistake as the 27B model: glossed the fatal-risk-columns paragraph, not the
  one that actually names `weekly.csv`. Two models, same wrong target. That is worth taking as a
  sign the brief left more room for this than intended, alongside being a real model miss.
- #1231. Repointed `kernel/src/icount.rs`'s comment at `miss-taxonomy-and-clockless-loops.md`, a real
  file, but the wrong one. The residual-window content actually moved to `known-residuals.md`, whose
  title is literally "Known residuals..."; the file the model chose only mentions the word
  "residual" once, in passing. It also rewrote the roadmap block's original 2026-09-19 sentence in
  place, rather than appending a dated correction beside it, which the brief asked it not to do.
- #1194. The most complete rename attempt of any model in this bake-off. 287 files touched, 36 real
  `git mv` renames, `scripts/` gone, `helpers/` in place. The ratification is recorded in

  mentions is a legitimate quotation about the rename itself, exactly what the brief asked to be
  preserved. It still breaks `script/lint`: three of the four bare-string
  `sys.path.insert(0, 'scripts')` calls the brief named explicitly (`script/lint`, `script/metrics`,

  gap, not a model defect, and it made no difference here: the substantive re-check above already

## Verification

Every "correct" and "wrong" above is this lane's own re-run, not the harness's self-report. Each
verdict comes from a fresh `git clone` of the surviving commit, with `script/lint` and
`script/citations --ratchet` (or `script/roadmap --check`, where the task touches the roadmap) run
and read directly. The two citation-ratchet tasks also got hand-built fixture commits, exercising
the exact move/new-citation distinction the brief specified. `script/lint` is red at both ratchet
tasks' shared base commit, on an unrelated pre-existing defect in `system_tests`'s package-boundary
registration. That is environmental, not either model's fault, and matches what round 1 found at the
same base for `f8018287a`.

## Cache hit rate and spend

Qwen3.8-27B (DeepInfra): **82.9%** of input tokens served from cache across the round
(70,116,256 of 84,607,727 input tokens, `cache_read` field in `spend.jsonl`, including the wasted
attempts from the process collision above). Qwen3.5-122B-A10B (AtlasCloud/Novita): **0%**, no
`cache_read` tokens at all across 535 requests, confirming the brief's own prediction that no
provider caches this route yet.

Total measured spend against the USD 40 cap, from `~/.local/open-lane/spend.jsonl` on cordoba: **USD
19.08**. That is both routes, everything since this lane's baseline (line 1241), including the
collision's waste. 27B: 10.02, of which 8.83 is the six clean runs above and the rest is waste plus
the gateway's own side-thread overhead. 122B: 9.06, all of it in the six runs above. Well under the
cap; no stop was needed.

## How long a lane would take on the 128GB tier (DGX Spark)

Same method as round 1: (new tokens across turns, i.e. input tokens not already cached, divided by
prefill rate) plus (output tokens divided by decode rate). The new-token count here uses the round's
own measured cache ratio, 82.9% reused for Qwen3.8-27B, applied to both models' input totals. The ratio
reflects how repetitive this agentic loop's turns are, not something specific to the provider's
cache. That makes it the least-bad stand-in for a model where no cache was measured.

Qwen3.8-27B: prefill 955 tok/s, decode 7.7 tok/s, same DGX Spark measurement round 1 already cited
(2,048-token depth prefill, FP8 no-speculation decode). New tokens ≈ 8.31M, output ≈ 712K:
8,310,000 / 955 + 712,000 / 7.7 ≈ **28.1 hours** for the six tasks, decode-bound (92,468 of the
101,169 seconds).

Qwen3.5-122B-A10B: no published DGX Spark, or comparable 128GB-tier, rate exists for this model or a
similar ~10B-active MoE at this size. Checked: the llama.cpp DGX-Spark/Strix-Halo benchmark PR round
1 cited, which has only dense Qwen3.8-27B at this tier, and the local-ai-registry lab-runs directory,
which has Apple and discrete-GPU runs only, nothing at this tier for a 100B+-total MoE. Estimated
(Est), scaled from the same measured 27B numbers. Prefill by active-parameter compute ratio: 27.8B
dense vs. 10B active gives 955 × 2.78 ≈ 2,655 tok/s. Decode by active-parameter memory-traffic ratio
at each tier's assumed quantization: 27B was measured at 8-bit dense, 27.8 GB/token; 122B locally
would run 4-bit, ~5 GB/token active; that ratio gives 7.7 × 5.56 ≈ 42.8 tok/s. New tokens ≈ 4.72M,
output ≈ 238K: 4,720,000 / 2,655 + 238,000 / 42.8 ≈ **2.0 hours** for the six tasks. Both estimated
rates are optimistic. They carry over a dense model's scaling law and ignore MoE routing and
shared-expert traffic, which cost real throughput that a clean ratio doesn't capture.

Every DGX Spark hour above is easily inside "hours, not days." Time was never round 1's problem for
the smaller tiers and isn't here either; correctness is what fails, on both models.

## Recommendation

Buy nothing on this evidence: correctness, not speed, is still the failure, and it got worse, not
better, when the model got smaller.

## BUGS

- Round 1's stop rule (three or fewer correct means stop) doesn't distinguish a model that fails
  early from one that fails late. Both of round 1's smaller candidates land at or under the line, and
  neither triggered stage 2. But a model this close to the line at n=6 is not distinguishable from a
  model well past it.
- The wrong-paragraph mistake on #1201, made identically by both models, is worth a second look at
  the brief rather than only at the models. The paragraph it led both of them to sits two paragraphs
  after the real target and discusses a similarly-shaped backfill story.
- The gate lock (PR #1429) has no way to name "this whole rename touches gate machinery on purpose"
  for a task like #1194, short of listing every path. It made no difference to this round's verdict.
  But the next rename-shaped open-lane task will hit the same wall.
- A forked subagent given a narrow read-only research directive still acted on inherited filesystem
  state from this lane's own context, and interfered with a running task. See the process note above.
  Forking into a lane that is concurrently mutating shared scratch state is unsafe as done here.
