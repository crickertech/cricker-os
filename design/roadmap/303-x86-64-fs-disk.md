# 303. x86_64's FS service has a server and no disk it can find

Promoted from
`design/roadmap/proposals/an-fs-service-with-no-disk-on-x86-64.md`, written by milestone 184's lane
on 2026-09-14. Minted **Gate: NONE**, on the grounds that milestone 215 had already routed a PCI
function's interrupt to a userspace driver on this port and milestone 164 had already packed
`redoxfs_server` in the x86_64 archive, so nothing here needed a board. That held: the whole
milestone was made on patagonia.

**The title is a statement about the past.** x86_64's FS service mounts a RedoxFS image off a
`virtio-blk-pci` function, `std::fs` runs there, and **unmodified `ripgrep` 14.1.1 prints the same
62 bytes it prints on aarch64 and riscv64**.

## The result that was the point

`design/fatal-risks/README.md` risk 1 ("only software written for nife runs on nife") had two legs of
three. Here is the third, from the x86_64 leg of `script/test`:

```
test kernel::user::ripgrep_tests::unmodified_ripgrep_runs_and_has_no_arguments_to_run_on ...
    rg printed 62 bytes:
rg: ripgrep requires at least one pattern to execute a search

ok
```

**Byte for byte what the other two architectures print**, from a third separately built binary
(4.1 MB, zero source changes, `helpers/build-ripgrep.sh` and nothing else). Compared rather than
recalled: `rg` was built for all three triples on this tree and the test run on each, and the three
transcripts hash to one value (`fa4b3016bc8a8335d12df349facc4379`), 62 bytes, `cmp` clean in both
directions. Three ELFs of three different instruction sets, 4.7, 10.7 and 4.1 MB, from the same
unpatched crates.io source. `notes/ripgrep-on-nife.md`'s
parity table now reads "built and run" on all three rows, and risk 1's green no longer needs the
words "on two of three architectures" that DECISIONS §19 would have made an overclaim.

## The three pieces the proposal named

**1. The lookup is transport-blind, and the ordering is the contract that made it safe.**
`virtio::find_block_device_n` walked virtio-mmio slots and returned a `VirtioMmioDevice`. It now
returns a `BlockDevice` (provisional name): a resolved `Transport`, the interrupt to bind, and the
IOMMU requester id when there is one, which are exactly the three things `fs_service::spawn_block_server`
and `virtio_service::wire` already needed. `fs_service::spawn_block_server` takes that instead of an
mmio slot, which is the transport seam doing for the FS server's disk what it already did for the
PCIe transport tests' disk.

**The ordering is mmio slots in slot order, then modern virtio-pci functions in bus:device.function
order**, and it was chosen rather than invented: it is the order `disk_service::devices` already
lists the milestone-57 roster in, and that function's own comment already called the agreement
between a listing and a wiring a promise. So the flat ordinal is the roster's row index, and the two
records cannot drift.

**Nothing moved on aarch64 or riscv64, and the reason is structural rather than lucky.** Both `virt`
boards carry five virtio-mmio block devices, and every ordinal any wiring asks for (0 the nifefs
disk, 1 the RedoxFS image, 2 milestone 37's crash disk, 3 and 4 milestone 57's GPT and blank disks)
is answered before the PCI half of the ordering is reached. Measured, not asserted: both legs pass
unchanged, below.

**2. The runner attaches the fixture.** `helpers/qemu-runner-x86_64.sh` attaches `-redoxfs.img` as a
second `virtio-blk-pci` function, behind the same `iommu_platform=on` the first one uses, and
`cargo xtask test`'s x86_64 leg calls `mkredoxfs` so a fresh fixture exists to attach. The order of
the two `-device` arguments is load-bearing (`q35` has no mmio bus, so ordinal 0 is the nifefs image
and ordinal 1 the RedoxFS one) and the file says so where a reader meets it.

The end-of-run image consistency check now runs for `--arch x86_64` too, on the RedoxFS image alone:
that leg writes it, so the check has a subject. The crash and blank images stay aarch64's and
riscv64's, because no x86_64 runner attaches those fixtures and a check whose subject did not happen
is worse than no check.

**And the test that writes the disk had to be widened, which the proposal did not foresee.**
`std_fs_reads_a_file_through_a_granted_directory_capability` was `#[cfg(target_arch = "aarch64")]`,
with riscv64 keeping its own copy in `riscv_virtio_tests`; x86_64 ran neither, so the `std::fs` half
this milestone exists to exercise would have been compiled and skipped on the one architecture that
had just been given a disk. It now runs on x86_64 as well. That is also what keeps
`xtask::redoxfs_check_after_run` honest: it is the only thing on this leg that writes `scratch`, and
the x86_64 leg runs last and regenerates the fixture, so without it the end-of-run host check would
open an image whose write never happened. The rest of the family (the per-file grant attacks) stays
on two architectures, for the "a second copy proves nothing new" reason those tests already carry.

**3. VT-d wanted nothing.** This was the piece the proposal could not price, and the answer is that a
second function behind the IOMMU needs no new mechanism: `virtio::register` already takes an
`Option<rid>` and `iommu::confine` already builds one domain per requester id. The second disk's rid
(`0x20`, for `00:04.0`) is carried through from `pci::find_block_device_n` the same way the first
one's always was, and the block server's 17-page DMA region is confined before the device is entered
in the table. Two virtio functions on one bus, each in its own domain, is the first time this tree
has done that on any architecture.

## What the second function on the bus turned out to say, which is a finding

Wiring the disk produced one line of QEMU stderr that milestone 164's lane had also seen and could
not explain:

```
qemu-system-x86_64: vtd_iommu_translate: detected translation failure (dev=00:03:00, iova=0xffde000)
```

**It is the IOMMU refusing a device this kernel does not drive, which is default-deny working.**
Three measurements say so and they were worth taking, because "an unexplained IOMMU fault beside a
confinement claim" is the shape of exactly the finding this project must not tidy away:

- The kernel's own fault register records `rid 0x18, code 0x2, addr 0xffde000`. `0x18` is
  `00:03.0`, the **first** virtio-blk function, the one the PCIe transport tests own and which
  nothing brought up in this run. Fault code 2 is "the context entry is not present": the unit was
  asked to translate for a device that has no domain, and refused.
- It is logged at confine time, **before any block I/O**, immediately after `virtio::register` builds
  the second disk's domain and invalidates. That is the shape of QEMU replaying mappings into every
  address space it has instantiated, not of a transfer going astray.
- With only one virtio-blk function on the bus, `ripgrep` runs and prints the same 62 bytes and
  **no fault is logged at all**. The fault needs an unclaimed function beside a claimed one, which is
  a configuration no architecture in this tree had before today.

215's reading of the neighbouring `Interrupt Mask set, irq is not generated` line was right and this
is its sibling: both come out of the VT-d unit itself, and neither is a confinement gap. What is new
is the recommendation below, that an unclaimed function should be confined to an empty domain rather
than left to be refused one request at a time.

## BUGS

- **A positional ordinal shifts silently when a fixture is missing, and the fall-through to PCI
  widened what it can shift into.** `find_block_device_n(2)` means "the third block device", not
  "the crash disk". On a boot where the runner built no crash image, ordinal 2 used to resolve to the
  GPT disk; it can now resolve to a virtio-pci function instead, and resolving a PCI ordinal brings
  the function up (sizes its BARs, enables bus mastering) where the mmio half reads two identity
  registers. Every runner in this tree builds every fixture, so no gate meets it, and the contract is
  documented on `find_block_device_n` itself. The fix is a wiring that names a disk rather than
  counting to it, which is milestone 57's roster half-built already and not this milestone's work.
- **The suite under real firmware still has no RedoxFS disk.** `helpers/qemu-uefi-x86_64.sh`
  attaches the nifefs image and the NVMe controller only, so `cargo xtask uefi-test` is unchanged at
  208 / 69 while the PVH leg is at 237 / 40, and the twenty-nine tests this milestone recovered are
  recovered on one of the two x86_64 boots. Adding the disk there is one `-device` line and a claim
  about firmware rather than about QEMU's loader, which is worth its own run.
- **x86_64 gets one fixture of five.** The RedoxFS image is attached; milestone 37's crash disk and
  milestone 57's GPT and blank disks are not, so `crash_disk_present`, `disk_service::start` and
  `disk_service::blank_disk` still answer "no such disk" on this architecture and their tests still
  skip. Nothing structural is in the way now that the lookup spans both buses: it is three more
  `-device` lines and three more `mk*disk` calls, deliberately not taken here so that one milestone
  proves one thing.
- **An unclaimed virtio function on the bus is refused one request at a time rather than confined
  once.** The VT-d record above is correct behaviour with an avoidable shape: a function nothing
  drives has no context entry, so every DMA it attempts faults individually and QEMU's log is the
  only place a reader meets it. Entering every enumerated function into an empty domain at boot
  would make default-deny explicit and turn the log line into a fault the kernel raised on purpose.
  That is a change to the confinement posture on three architectures and is a proposal
  (`design/roadmap/proposals/an-unclaimed-function-behind-the-iommu.md`), not a fix smuggled in here.
- **`BlockDevice` is a provisional name**, along with `virtio::find_block_device_n`'s widened meaning
  and `pci::find_block_device_n`. calef names types and public functions (AGENTS.md); this lane
  shipped names and says so rather than waiting.
- **The x86_64 `ripgrep` binary is not in any gate.** `helpers/build-ripgrep.sh` fetches from
  crates.io and nothing in `script/test` runs it, so the transcript above is reproducible only after
  somebody builds `rg`. That is DECISIONS §46's posture and unchanged by this milestone; what changed
  is that building it is now sufficient.

## Index row

x86_64's FS service mounts a real RedoxFS image and **unmodified `ripgrep` 14.1.1 prints the same 62
bytes there that it prints on aarch64 and riscv64**, which is the third leg `design/fatal-risks/README.md`
